## 二、各阶段详细设计

### P0 · 契约与字段定义

先统一“变异 + 文献上下文 + 输出结论”的中间表示，避免 UI、解析、家系抽取各自定义字段。

**交付物**
- `doc/contract/variant.md`：变异对象。建议字段包括 `raw_input`、`genome_build`、`transcript`、`gene`、`c_hgvs`、`p_hgvs`、`ref`、`alt`、`coordinates`、`rs_number`、`source_format`、`confidence`、`fallback_chain`。
- `doc/contract/family.md`：家系对象。覆盖成员关系、表型状态、携带状态、变异分布、父母验证结果。
- `doc/contract/result.md`：最终输出 schema。需兼容现有 `render_result` 的 `sections` 结构，同时新增结构化字段：`parental_verification_status`、`parental_verification_basis`、`disease_category`、`warnings`。

**验收点**
- 最终结论必须显式展示“是否通过父母验证”及依据；未报道时标记 `not_reported_in_source`，不能留空。
- 基础文献总结必须包含题目、摘要/研究对象、疾病大类、关键结论。

**开放问题 → Q1-Q4**

---

### P1 · 解析最小内核

将输入识别与 UI 解耦，先提供一个可测试的解析入口，供 Streamlit 页面、后续检索和 skill 复用。

**新增模块（建议放 `variant/`）**
- `format_detector.py`：识别 5 类标准格式。
- `variant_request.py`：把结构化字段或单行文本转成 P0 定义的请求对象。
- `validation.py`：校验允许提交的输入组合。

**支持的输入组合**
- `transcript + c_hgvs`
- `transcript + p_hgvs`
- `gene + c_hgvs`
- `gene + p_hgvs`
- `genome_coord`
- `rs_number`
- `free_text`

**注意**
- `rs_number` 和 `free_text` 允许提交，但应标记为待解析或低置信度候选，不能被 UI 必填规则拦截。
- P1 只做识别、拼接和请求对象生成；不承担 Mutalyzer 归一化、转录本排序和外部检索。

**开放问题 → Q5-Q8**

---

### P2 · 输入层重构

**改造点**
- `app/pages/2_OpenAI_Compatible.py`、`app/main.py`：将单行 `st.text_input` 拆成结构化字段。
- 新增字段：
  - `transcript`（NM 号，可选）
  - `gene`（HGNC 符号，可选）
  - `c_hgvs` / `p_hgvs`
  - `genome_coord`（GRCh37/GRCh38 下的 chr + pos + ref/alt）
  - `rs_number`
  - `free_text`
  - `genome_build`：默认 GRCh37，可选 GRCh38
- 实时拼接预览：调用 P1 内核生成标准化请求对象。
- 示例区：展示 5 个标准格式、`rs` 号和自由文本示例。

**验收点**
- 用户无需手工拼接完整 HGVS 字符串。
- 输入不完整时给出字段级提示；`rs_number` / `free_text` 不被标准格式校验误拦。
- 解析失败时把原始输入和失败原因写入 `mutalyzer_diagnostics`，供 P7 展示。

**开放问题 → Q9-Q11**

---

### P3 · 归一化与转录本解析

**新增模块**
- `hgvs_normalizer.py`：调用 `mutalyzer.nl/api/normalize/`，统一输出 `{transcript, c_hgvs, p_hgvs, ref, alt, genome_build}`。
- `transcript_resolver.py`：用户指定转录本优先；未指定时按内部 DB / MANE Select / RefSeq fallback 顺序尝试。
- `c_to_p.py` / `p_to_c.py`：双向反推。优先使用 Mutalyzer，本地逻辑仅作兜底。

#### P3.1 · 内部转录本 DB 接入
- 先确认内部 DB 的访问方式、认证和字段定义。
- 最小字段：`gene -> canonical_transcript`、`transcript -> preferred_status`。
- 内部 DB 不可用时退化到公开数据源，例如 MANE Select / RefSeq。

**开放问题 → Q12-Q16**

---

### P4 · 补充检索

**P4.1 dbSNP 编号搜索**
- 路径：`rs<number>` -> NCBI E-utilities / 内部镜像 -> 候选变异 -> P3 归一化。
- 缓存：同一 `rs` 号 24 小时内不重复请求；缓存命中需记录数据来源和时间。

**P4.2 自由文本兜底**
- 用 LLM 对非标准描述做候选提取，例如 `chr7q31 deletion`、`IVS2-1G>A`。
- 多候选时返回置信度和候选列表，低于阈值要求人工确认。
- 解析失败时可进入“整篇文献问答/基础总结”模式，但需要明确标记未定位目标位点。

**开放问题 → Q17-Q19**

---

### P5 · 家系抽取扩展

**4 维度结构化**
1. **成员关系**：父母 / 兄弟姐妹 / 子女 / 祖辈。
2. **表型状态**：`affected` / `unaffected` / `unknown`。
3. **携带位点状态**：`carrier` / `non_carrier` / `unknown`。
4. **变异分布结果**：`de_novo` / `inherited_maternal` / `inherited_paternal` / `both` / `unknown`。

**实现路径**
- 抽取源：BioC XML 中的表格、正文段落；是否支持额外家系表另行确认。
- 提示词 + JSON Schema 输出，与 P0 契约对齐。
- 不一致检测：受影响但非携带、未受影响但携带等情况进入 `warnings`。
- 缺失透明化：未提及字段统一标记 `not_reported_in_source`。

**最终输出要求**
- 单独生成“父母验证结论”字段，说明通过/未通过/未报道，以及依据来自表格、正文还是推断。

**开放问题 → Q20-Q22**

### P6 · PDF / BioC 预处理

会议中“无位点也要总结”适合作为预处理/兜底能力实现，但当前仓库已有链路主要是 PMID -> BioC XML 下载，不等同于 PDF 转 BioC。

**已有能力**
- `app/data_io/download_papers.py`：按 PMID 从 NCBI BioNLP API 下载 BioC XML 到 `./data/xml_papers`。
- 仓库内已有 `xml/` 示例文件，可用于调试 BioC / XML 解析。

**待新增或调研**
- 上传 PDF -> 文本 / 表格 / BioC-like 结构：评估 PubTator、Grobid 或内部模型。
- 无目标位点时：跳过 P3-P5，输出基础文献总结（题目、摘要/研究对象、疾病大类、关键结论、未定位原因）。
- PDF 解析质量评分：区分“文献未报道”和“解析失败/抽取不足”。

**开放问题 → Q23-Q24**

### P7 · 可观测性

**复用现有 `mutalyzer_diagnostics`**（`app/core/query.py:30`），扩展为完整 trace：
- 输入解析：原始输入、识别格式、字段校验结果、失败原因。
- 归一化：Mutalyzer 端点、状态、错误。
- 转录本匹配：候选列表、最终选择、选择原因。
- 检索：chunk 数、匹配模式、protein short form。
- 家系抽取：抽取成员数、各维度覆盖率、父母验证结论来源。

**UI 改造**
- 新增 `st.expander("诊断信息")`，默认折叠。
- 支持复制或下载 trace，便于远程排错。

## 三、待需求方/工程澄清的问题

### 契约与输出
- **Q1**：最终结论中“父母验证”展示为单独字段，还是合并到 PM3 证据结论中？
- **Q2**：父母验证状态枚举是否采用 `verified` / `not_verified` / `not_reported` / `conflicting`？
- **Q3**：疾病大类的标准来源是什么：人工枚举、OMIM/Orphanet、内部字典，还是 LLM 分类？
- **Q4**：未报道信息统一展示为 `not_reported_in_source`，还是转成中文提示？

### 输入与 UI
- **Q5**：5 标准格式之外的输入（例如 `NM_004004.5（c.71G>A）`、中文描述）需要兼容到什么程度？
- **Q6**：标准格式不完整时，UI 是硬阻断，还是允许提交并返回解析失败原因？
- **Q7**：GRCh38 切换是 per-query 级别，还是全局默认设置？
- **Q8**：示例展示是静态样例，还是支持从历史查询复制？
- **Q9**：`rs_number` 和 `free_text` 是否允许单独提交？
- **Q10**：自由文本候选是否需要用户确认后才继续归一化？
- **Q11**：结构化输入是否保留原单行输入作为高级模式？

### 归一化与转录本
- **Q12**：Mutalyzer 是否原生支持 GRCh38？如果不支持，liftover 放在客户端还是服务端？
- **Q13**：c. <-> p. 反推时返回单个最优结果，还是多个候选？
- **Q14**：主转录本来源是内部 DB、MANE Select，还是二者合并排序？
- **Q15**：转录本 fallback 顺序如何定义？
- **Q16**：内部转录本 DB 的访问方式、认证、QPS 上限分别是什么？

### 补充检索
- **Q17**：dbSNP 查询走 NCBI E-utilities、内部镜像，还是二者 fallback？
- **Q18**：自由文本置信度阈值是多少？低于阈值时如何提示用户？
- **Q19**：自由文本解析失败时是否进入整篇文献问答/基础总结模式？

### 家系抽取
- **Q20**：家系信息仅从 XML/PDF 的表格和正文抽取，还是支持上传额外家系表？
- **Q21**：成员关系是否需要输出 pedigree 图，还是结构化 JSON 即可？
- **Q22**：表型与携带状态冲突时，标记 warning、强制人工 review，还是过滤？

### PDF / BioC
- **Q23**：PDF -> 结构化文本使用 PubTator、Grobid、内部模型，还是先只支持 BioC XML？
- **Q24**：基础文献总结是否需要引用原文片段和长度上限？

### 可观测性 / 集成
- **Q25**：诊断信息是否要支持下载 JSON，用于工单或问题复现？
- **Q26**：skill 化目标是外部 agent 调用，还是仅服务内部 Streamlit？
- **Q27**：是否有脱敏 / 隐私要求，尤其是缓存和 trace 下载？

## 五、风险与依赖

| 风险 | 影响 | 应对 |
|------|------|------|
| 输出契约未强制父母验证字段 | 最终结论仍遗漏关键依据 | P0 将父母验证设为必显字段，未报道也显式标记 |
| P1/P2 职责混乱 | UI 先写临时解析逻辑，后续返工 | 先做解析最小内核，再让 UI 调用 |
| 内部转录本 DB 接口未公开 / 不可用 | P3 阻塞 | 提前对齐 API；fallback 到 MANE Select / RefSeq |
| Mutalyzer GRCh38 支持不明确 | 归一化结果不稳定 | 先确认能力；必要时增加 liftover 服务 |
| `rs` / 自由文本被 UI 校验拦截 | 补充检索无法触发 | P1/P2 将其列为合法输入模式 |
| PDF 解析质量差 | 基础总结和家系抽取不可信 | 引入质量评分，区分未报道和解析失败 |
| 家系维度抽取冲突 | 结论可信度下降 | schema 校验 + warning + 人工确认入口 |
